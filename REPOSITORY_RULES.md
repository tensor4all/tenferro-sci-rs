# Repository rules

Rules specific to tenferro-sci-rs. The rules shared by every tensor4all Rust
repository are in
[tensor4all-meta · docs/contributing/rust-repositories.md](https://github.com/tensor4all/tensor4all-meta/blob/main/docs/contributing/rust-repositories.md),
and the shared agent rules in
[tensor4all-agent-rules](https://github.com/tensor4all/tensor4all-agent-rules/blob/main/rules/index.md).
The design these rules serve is
[tensor4all-meta · docs/design/tenferro-sci.md](https://github.com/tensor4all/tensor4all-meta/blob/main/docs/design/tenferro-sci.md).
Where this file and the code disagree, the code wins and this file is fixed.

## Crate Layout

- **Independent cores** hold algorithms that need only vector operations
  (Krylov methods, scalar special functions, quadrature nodes and weights,
  interpolation weights). They are pure Rust, generic over caller-defined
  vector or scalar types, and never depend on a tenferro crate. A core that
  already exists elsewhere (for example `krylov`) is used as a dependency, not
  copied in.
- **`tenferro-<module>` crates** depend on released tenferro crates and add
  `Vector`/`LinearMap`-style implementations for tenferro tensors, autodiff
  rules, batching, traced use and GPU execution. A user depends on one
  `tenferro-<module>` crate; it re-exports the core it wraps.
- Crate names follow SciPy's module names: `tenferro-krylov`,
  `tenferro-optimize`, `tenferro-special`, `tenferro-integrate`,
  `tenferro-interpolate`. There is no facade crate.
- Matrix functions (`expm`, `logm`, `sqrtm`), Schur and polar decompositions
  belong in `tenferro-linalg` in tenferro-rs, and FFT variants in
  `tenferro-fft`, not here.

## Workspace, Versions And Releases

- One Cargo workspace. The first PR that adds a crate also adds the root
  `Cargo.toml`, with `[workspace.dependencies]` for every shared dependency and
  `rust-version` matching tenferro-rs.
- Every crate in the workspace carries the same version and is published in the
  same release. A release bumps all of them.
- tenferro crates are pinned once, in `[workspace.dependencies]`, to released
  versions. No git or path dependency on tenferro-rs in a committed manifest.
  A change that needs an unreleased tenferro API waits on its branch until that
  API is released; `.github/workflows/upstream-main.yml` checks the workspace
  against tenferro-rs `main` every day.
- Nothing is published to crates.io without the maintainer's explicit approval
  of that specific package and version.

## Pure Rust

- No C, C++ or Fortran build-time dependency and no `build.rs` that compiles
  native code. Native libraries (CUDA, HIP, Metal) are loaded at run time, as in
  tenferro-rs.
- GPU device code is the exception: kernel source compiled at run time (NVRTC
  or HIPRTC) may include upstream C++ headers such as SciPy's xsf, with their
  license recorded as for any port.

## Numerical Validation

- Every function is checked against reference values with a stated tolerance:
  mpmath (arbitrary precision) as ground truth, and SciPy for parity. A test
  that only checks that a result is finite, or has the right sign, is not
  validation.
- Reference data is generated by a committed script that records the SciPy,
  mpmath and Python versions and the generation date. Regenerating it is a
  separate commit.
- When porting, port the upstream tests and reference tables first, then the
  implementation.
- Tests are small and fast: fixed seeds, minimal cases, exact or
  tolerance-stated assertions. No test takes tens of seconds.
- A bug found in an upstream library or in reference data (mpmath, SciPy,
  xsref, ...) is recorded in [`docs/upstream-issues.md`](docs/upstream-issues.md)
  with its evidence and what this repository does about it, whether or not it
  is reported upstream.

## Autodiff

- Algorithms written as compositions of tenferro operations inherit autodiff;
  do not add rules for them.
- Iterative solvers and optimizers (eigen- and linear solves, minimizers, root
  finders, ODE solvers) get explicit rules by implicit differentiation or adjoint
  methods. Do not differentiate through the iterations.
- Every autodiff rule is checked against reference derivatives or finite
  differences, including complex inputs where the function supports them.

## CPU And GPU

- Every algorithm runs on the CPU engine first.
- A GPU path is added only where it pays: elementwise functions, large
  matrix-vector products, or many small problems solved as one batch. The PR
  that adds it carries a measurement against the CPU path.
- No hidden device transfers and no global state: every call takes the
  caller's engine or execution context, as in tenferro-rs.

## Kernels

Contractions, GEMM, decompositions and solves go through the owning
abstraction (tenferro's einsum and linalg, tcontract, tlinalg, colmat). Do not
write a repository-local scalar accumulate loop for them. If a loop genuinely
cannot be expressed that way, put `// contraction-kernel-ok: <reason>` directly
above it and explain the exception in the PR.

## Ports And Provenance

Follow the shared
[provenance rules](https://github.com/tensor4all/tensor4all-agent-rules/blob/main/rules/common/provenance.md).
In addition:

- A file translated from another project names, at the top, the upstream
  project, file and commit it was ported from, so later upstream fixes can be
  diffed.
- The upstream license text ships with the crate, and the crate's `license`
  field states the combination, for example
  `(MIT OR Apache-2.0) AND BSD-3-Clause`.
- Code written independently from a mathematical reference (for example DLMF)
  says so.
- Do not port from GSL (GPL) or Numerical Recipes (restrictive license).

## Public API And Documentation

- No `unwrap()` or `expect()` in library code. Public errors use `thiserror`,
  and every public function returning `Result` documents its errors.
- Every public item has a doc example that compiles and runs; no `ignore` or
  `no_run`.
- When a function with a SciPy counterpart is added, add its row to the
  SciPy-to-tenferro-sci mapping table in the crate's documentation.
