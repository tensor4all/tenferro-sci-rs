# Reference data of `minimize::lbfgs`

SciPy 1.16.3 runs of `scipy.optimize.minimize(method="L-BFGS-B", bounds=None)`, recorded for the tests
`../../lbfgs_replay.rs`, `../../lbfgs_direction.rs`, `../../lbfgs_live.rs` and the unit tests of
`../../../src/lbfgs/twoloop.rs`. Generated by `scripts/gen_minimize_lbfgs_reference.py`
(`uv run scripts/gen_minimize_lbfgs_reference.py` from the repository root; regenerating is a separate commit).
Tracking issue: tensor4all/tenferro-sci-rs#40.

Produced on macOS arm64, Python 3.12, SciPy 1.16.3, NumPy 2.3.5, mpmath 1.3.0 (Accelerate BLAS, Apple libm); the
versions and the date are in the `#` header lines of every file. The CI platform (ubuntu-24.04, OpenBLAS) runs `--check` in the `minimize-reference` job; its first run found the
platform dependence described below.

## The protocol: what exactly was called

Every run is executed twice, and the generator asserts that the two agree on the whole sequence of evaluated points,
the final point, `nit`, `nfev`, `status` and `message`:

1. **The public call**, with *every* option passed explicitly (the `call` column of `runs.csv`; commas are replaced by
   semicolons in the file):
   `minimize(fun, x0, jac=True, method='L-BFGS-B', bounds=None, options={'maxcor': …, 'ftol': …, 'gtol': …,
   'maxfun': …, 'maxiter': …, 'maxls': …})`. SciPy's defaults are `maxcor=10, ftol=2.220446049250313e-09 (=1e7 eps),
   gtol=1e-5, maxfun=15000, maxiter=15000, maxls=20`. `maxls` is recorded for every run.
2. **A replica of `_minimize_lbfgsb`'s loop** (`_lbfgsb_py.py`) around `scipy.optimize._lbfgsb.setulb`, which reads SciPy's
   internal state at every request: `isave` (`col`, `head`, `iter`, `iupdat`, `nskip`, `ifun`), `dsave` (`theta`, `stp`)
   and the workspace `wa` (the stored pairs `S`, `Y`, the direction `d`, the saved point `t` and gradient `r`). The
   workspace layout is the partition `setulb` computes (`__lbfgsb.c`); the indices `mainlb` uses are shifted by 21 in the
   array `setulb` receives. This is how restarts (`col` dropping to 0 at `iter > 0`), the pairs and the direction are
   known, not inferred.

SciPy's `message` is mapped to the Rust `Termination` through the task code (not the `status` integer, which is 1 for an
`ABNORMAL` end when `nfev > maxfun`): `CONVERGENCE: NORM OF PROJECTED GRADIENT <= PGTOL` → `grad_tol`, `…RELATIVE
REDUCTION OF F…` → `f_tol`, `STOP: TOTAL NO. OF ITERATIONS REACHED LIMIT` → `max_iter`, `STOP: TOTAL NO. OF F,G
EVALUATIONS EXCEEDS LIMIT` → `max_eval`, `ABNORMAL` → `line_search_failed`.

Nothing in the data is a NaN or an infinity: SciPy's behaviour there (it resets the memory and burns the remaining
`maxls` trials; NaN at `x0` gives `ABNORMAL` after 21 evaluations) is deliberately *not* ours (decision (b) of #38: stop
at the last finite iterate), so those paths are tested with hand-fed values in `../../lbfgs_termination.rs` and not replayed.

Problems (the Rust tests mirror them in `tests/lbfgs_common/mod.rs`): Rosenbrock n = 2 (two starts) and n = 5, Beale,
Himmelblau, Powell's singular function, and the quadratics `½(x−x*)ᵀA(x−x*)`, `A = P diag(λ) P`, `P = I − 2uuᵀ`,
`u ∝ (1,…,n)`, `λᵢ = κ^(i/(n−1))` (κ = 1, 1e2, 1e4; n = 5, 10), `x* = (1,…,n)`, `x0 = 0`.

Not recorded: a run with a skipped update (`nskip > 0`); the deterministic search over `maxls` and the problems found
none. The skip rule is covered by the unit tests of `src/lbfgs/memory.rs` instead.

Not recorded either: a line search that ends in a `dcsrch` *warning* (rounding errors, xtol, stpmax, stpmin). All 1021
searches that ended with an accepted step ended with `CONVERGENCE`. `lnsrlb` accepts a warning like a convergence (task
`NEW_X` at the last trial, even when `f` increased), so this is pinned by a hand-fed scenario instead: the generator's
`scripted_checks()` feeds SciPy 1.16.3 a scripted sequence of `(f, g)` (x0 = [0], f0 = 4, g0 = [−1]; then (3.5, −0.95),
then (10, 1) four times) and asserts the requests `0, 1, 5, 1.3552244689139858, 1.0030498702469033, 1.0`, the result
`CONVERGENCE: RELATIVE REDUCTION OF F`, `nit = 1`, `nfev = 6`, `x = [1]`, `f = 10`: the search ends with
`WARNING: XTOL TEST SATISFIED`, the last trial becomes the iterate although `f` rose from 4 to 10, and the one-sided
function test stops the run. `../../lbfgs_termination.rs` replays the same script.

## Two claims, two mechanisms

1. **Parity: the Rust implementation against SciPy's committed data** (the Rust replay, `tests/lbfgs_replay.rs`). The requested
   points must agree within a *derived* bound, `C_X ε x_scale + 2 x_slack`, on each run's comparison prefix; counts and
   termination agree exactly on the whole run. The bound is derived from the algorithm (rounding of the updates plus SciPy's
   measured direction error), `C_X = 32` is calibrated on the float64 mirror with a margin (see "How the tolerance was derived").
2. **Reproducibility: SciPy regenerated on another platform against SciPy committed** (`--check`, run in CI on Ubuntu/OpenBLAS
   while the data come from macOS/Accelerate). Counts, termination, message, call, caps, flags and row keys are **exact**; the
   bounds section (caps and comparison prefixes must stay inside the bounds on the running platform) is unchanged; SciPy's float
   columns (the *trajectory* columns below) are compared with **one named constant, `SCIPY_REPRO_RTOL = 1e-6`**, per component,
   `|a − b| ≤ SCIPY_REPRO_RTOL · max(|a|, |b|, scale)`, on the same comparison prefix as the replay (rows past it: exact columns
   only). `scale` is the largest absolute component of that column over the run's compared rows (committed values); it makes
   1-ulp differences of components near 0 pass by construction (an ulp of the large components is ≪ 1e-6 of the scale).

   `SCIPY_REPRO_RTOL` is a **calibrated reproducibility tolerance of SciPy across BLAS/libm, not derived from the algorithm.**
   Calibration (Ubuntu CI run 46134161576, all compared rows of every column, not a sample): the largest absolute differences were
   `evals` x 7.2e-12, f 8.7e-11, g 2.1e-8; `searches` x_base 6.5e-12, g_base 2.7e-9; `pairs` s 9.1e-12, y 2.4e-8; `runs` x 1.1e-13,
   f 5.7e-14, ginf 3.7e-13. Divided by the smallest run scale of that column in the compared prefixes (1.2, 14.2, 5.0, 1.2, 5.0,
   0.18, 0.67, 1.2, 14.2, 5.0) the observed relative difference is bounded by 6e-12, 6e-12, 4.2e-9, 5.4e-12, 5.4e-10, 5.0e-11,
   **3.5e-8** (pairs y, the largest), 9e-14, 4e-15, 7e-14. The constant is 1e-6: a margin of at least 28x over the largest. Every
   `--check` run prints the observed maximum per column and overall next to the constant (the maintainer's condition for a
   calibrated constant); an observed maximum above ~1e-6 would mean the data, not the constant, is in question.

   Why two mechanisms: an earlier attempt used the derived parity bound for the cross-platform check as well and failed on
   Linux (148 values outside it in run 46134161576, including 1-ulp differences): a bound derived for "an implementation that
   follows the algorithm" says nothing about how SciPy's own BLAS/libm calls round, and a bound for SciPy's rounding is an
   empirical property of those libraries. In three CI runs (46133315711, 46133534426 and 46134161576, each with the full check)
   the exact columns, i.e. every path, count, termination, message and cap, were **identical on Linux** (0 exact mismatches); only
   floating-point values differ, at the 1e-8 relative level at most on the compared prefixes.

## What `--check` compares

`uv run scripts/gen_minimize_lbfgs_reference.py --check` regenerates everything in memory, compares and writes nothing.
It prints a summary per file and column (rows compared, rows outside, the largest absolute difference, the observed maximum
relative difference next to the constant and the margin) and **every mismatch of an exact column in full**, with the list of runs whose path or options changed, so
one CI log answers "did any run change its counts or termination on this platform". Every comparison runs before the verdict: a committed cap (or run) outside the bounds on the running platform is listed under
"bounds on this platform" after the summaries and never hides other mismatches. Exit 1 on any exact mismatch, any
trajectory value outside its tolerance, or any bound violation.

Why this is needed: SciPy's trajectory differs at rounding level between platforms (Accelerate/Apple libm vs
OpenBLAS/glibc: the quadratics' matrix–vector products and the dot products inside SciPy's C code sum in a different order,
and the Rosenbrock problems amplify it). The first Ubuntu 24.04 run (PR #41, CI run 46132168523) showed 764 mismatches: the
final `ginf` of the same run differs in the 7th digit, and the platform-dependent choices of the generator changed.

| kind | columns | rule |
|---|---|---|
| exact | ids, options (`ftol`, `gtol`, `x0` as floats), `call`, `message`, `termination`, `nit`, `nfev`, `njev`, `nrequests`, `nskip`, `nrestart`, `nsearch`, `maxiter`, `maxiter_cap`, `replay`, the keys and the number of rows of every file, `accepted`, `search`, `ifun`, `col`, `iter`, `restart` | string equality. A difference means the path of a recorded run changed on that platform: the run leaves the parity set with a documented reason; the check is never loosened |
| trajectory (SciPy's own values) | `evals.csv` `x`, `f`, `g`; `runs.csv` `x`, `f`, `ginf`; `searches.csv` `x_base`, `g_base`; `pairs.csv` `s`, `y` | `SCIPY_REPRO_RTOL` per component with the run scale ("Two claims"), on the comparison prefix |
| diagnostic | `x_scale`, `x_slack`, `d`, `d_exact`, `d_scale`, `gamma_*`, `stp0`, `dir_ratio`, `mirror_ratio`, `cap_first_bad`, `uncapped_nsearch`, `cmp_nsearch` (checked: not shorter on the running platform), `caps.csv` | not compared; the generator checks the regenerated ones against their bounds (a run, or a committed cap, outside the bounds on the running platform aborts with a message) |

The derived position bound below (ε = 2⁻⁵², `C_X = 32`, the committed `x_scale`, `x_slack`) is the **parity bound of the Rust replay**;
`--check` does not use it:

* `|Δxᵢ| ≤ C_X ε x_scaleᵢ + 2 x_slackᵢ`: `x_scale` is the running sum of the magnitudes whose rounding enters the point,
  `x_scaleᵢ = |x₀ᵢ| + Σⱼ (|αⱼ dⱼᵢ| + |x_{j+1,i}|) + |x_base,i| + |α dᵢ|`, so one fused update `x + α d` (error ≤ ε|α d| + ε|x_new|
  per implementation, two implementations) is covered by construction. `x_slackᵢ` is the accumulated deviation of SciPy's direction
  from the exact one (measured against mpmath), counted twice.

**What is compared, row by row: the comparison prefix.** The bound models rounding, not its *amplification* by the problem
(the line search and the matrix `H` respond to a perturbation of an iterate). So every run carries `cmp_nsearch`: the number of
line searches whose requested points stay within `C_X / 4 · ε x_scale + 2 x_slack` of SciPy's for the independent float64 mirror
(the generator's `Mirror`); the first search that exceeds it ends the prefix. **Only rows inside the prefix are compared by value**
(`evals.csv` rows with `search < cmp_nsearch`, `searches.csv` rows with `j < cmp_nsearch`, pairs formed by such searches,
`runs.csv` `x`, `f`, `ginf` only if the whole run is inside the prefix). **Rows past it, and counts-only rows, are compared by
counts, termination and the other exact columns only**; the summary of `--check` prints how many rows were skipped per file. The
Rust replay uses the same prefix and the same formula, so replay and `--check` make the same claim. `cmp_nsearch` is a
diagnostic column: `--check` fails if the prefix on the running platform is *shorter* than the committed one (the committed
prefix is then outside the bound there), never by changing it. 18 of the 49 replayed runs have a prefix shorter than the run:
the Rosenbrock-2/5 runs (7 line searches; the runs have 36–55), `quad5_k1e4` (12 of 30–36) and `m3_rosen5` (6 of 23); see "The margin rule".

**The earlier scale was replaced.** The first version used the absolute-value recursion of the two-loop (`Σ|terms|` with every
sign positive), which compounds along the recursion: on `default_rosen2` it grew to 4.6e15 over 36 iterations, and
`C_X ε x_scale` was about 33 in x at the end of that run: vacuous for the replay and for this check. With the running magnitude
sum the same run has `x_scale` ≈ 9 at its last compared evaluation and a position tolerance of 7e-14 (2e-13 at the last
evaluation of the run), against 33 before. The price is honest: where the old scale hid the amplification inside a huge
tolerance, the prefix now shows where it starts. Tolerances relative to the values in the committed data (inside the prefixes):
`x` median 6e-14, 95th percentile 1e-12, maximum 5e-11 of `‖x‖∞`; `g` median 1e-10, 95th percentile 3e-6, maximum 52 (late in
runs where `|g|` is below the absolute floor `4 L ‖tol_x‖`); `f` median 6e-13, 95th percentile 2e-7, maximum 333 (the same).

**The margin rule (every cap and every comparison prefix).** Committed value = (the smallest first-outside index observed on any
checked platform) − `PREFIX_MARGIN` (2 line searches), applied uniformly and never lengthening anything; `C_X` and the bounds are
unchanged. Line searches are numbered from 0; a cap or prefix of `n` keeps searches `0 … n − 1`, and "first outside" is the index of
the first search outside the bound, so a value is valid iff it is `≤ first outside`, and the rule keeps it `≤ first outside − 2`.

Why a margin: the **same image and the same code gave different prefixes on two GitHub runners**: `quad5_k1e4` (three runs) had its
first search outside the mirror bound at 15 in CI run 46134596827 (and on macOS) and at **14** in run 46135341702 (PR #42), with 0
exact mismatches and 0 values outside `SCIPY_REPRO_RTOL` in both. The runners differ in CPU microarchitecture and OpenBLAS kernel
dispatch, so a prefix or cap at margin 0 on one machine is fragile everywhere, not only across macOS and Linux.

| `quad5_k1e4` (`default_`, `tight_`, `live_`) comparison prefix | 15 | 14 (run 46135341702) | **12** |

Caps are the number of line searches kept (= `maxiter`, accepted iterations); the caps' evidence is the first search outside the bounds
(direction criterion on macOS, `cap_first_bad`; the earlier mirror criterion for the Linux values). The generator keeps these
numbers in `LINUX_FIRST_OUTSIDE`, `OBSERVED_CAP_OUTSIDE` and `PREFIX_MARGIN`, and takes the caps, the `tight` gtols, the search
picks and the counts-only live rows from fixed tables, so no platform-dependent choice remains. `--check` still fails when a
committed cap or prefix leaves the bounds on the running platform, and **prints the margin of every prefix and cap** (first outside
here minus the committed value, smallest first) in its "margins" section, so every CI log shows how close each one is; the data
column `first_outside` records the raw first search outside the mirror bound on the generating platform.

The generator also asserts the coverage the tests rely on (every termination, a restart ending in each of three ways, the
counting cases).

## How the tolerance was derived

The replay feeds SciPy's `(f, g)` to the Rust state and compares the requested point with SciPy's. A requested point is
`x_base + α d`, `d = −H g` (two-loop), α from the line search. Rust's `x_base` is its own accepted iterate, so the error
accumulates over the steps taken. For component `i` the test allows

    |x_rust,i − x_scipy,i|  ≤  C_X · ε · x_scale,i  +  2 · x_slack,i          (ε = 2⁻⁵², C_X = 32)

* `x_scale,i = |x₀,i| + Σⱼ (|αⱼ dⱼ,i| + |x_{j+1,i}|) + |x_base,i| + |α d_i|`: the magnitudes whose rounding enters the point
  (Higham, *Accuracy and Stability of Numerical Algorithms*, 2nd ed., §3.1: a sum of terms is computed to within
  `γₙ Σ|terms|`, `γₙ = nε/(1−nε)`), with the *actual* direction and step, no recursion. It is the same quantity for the replay
  (Rust vs SciPy) and for `--check` (SciPy vs SciPy): "the same claim".
* `x_slack,i`: the sum over the steps so far (and the current one) of `|α_j| · |d_scipy − d_exact|_i`, counted twice in the bound (each implementation deviates from the exact direction by about that): SciPy's *own*
  deviation from the exact direction, measured against mpmath, not assumed. SciPy's compact-representation direction is
  less accurate than a two-loop recursion on small memories: relative to `d_scale` it deviates by up to **43.8 ε** on the
  committed runs (`dir_ratio`), against 1.3 ε for a float64 two-loop recursion (`../../../src/lbfgs/twoloop.rs`,
  checked on all 1028 searches).
* **`C_X = 32` is measured, not derived from `n` and `m`.** A float64 mirror of the algorithm the Rust code follows
  (`Mirror` in the generator: the ask/tell state machine described in the module docs of `minimize::lbfgs`, on Python's
  `DCSRCH._iterate`, which `linesearch::MoreThuente` ports) replays every run. The generator measures, for each run, the longest prefix in which the mirror agrees and the ratio
  `(|Δx| − 2 x_slack) / (ε x_scale)` of each line search (`mirror_ratio`) is at most `C_X / 4 = 8` (this defines `cmp_nsearch`, the
  comparison prefix), and, for the cap, SciPy's own direction is within `C_DIR / 2 = 64` of exact (`dir_ratio`, `C_DIR = 128`). The factor 4 is a margin: a throwaway implementation
  of the algorithm was up to twice as far from SciPy as the mirror (27.5 against the mirror's 13.6 on a longer prefix), so
  the constant `C_X` is never raised and the prefix is shortened instead. The Rust implementation is independent of the
  mirror; its PR must report its own maximum. If it exceeds the bound, that is a finding to explain, not a constant to widen.
  The constant is one named value (`C_X` in `tests/lbfgs_common/mod.rs`) and every replay failure prints the observed
  maximum ratio and the bound.
* **Which runs are capped, and why the cap is data.** Five runs of the `memory` group (`maxcor` = 1, 3) end early. Their
  `maxiter` is the `maxiter_cap` column of `runs.csv` (`none` for every other run), chosen by **the margin rule** from the first search outside the
  bound on every checked platform: every line search before the cap has direction error
  ≤ `C_DIR / 2`, and the run stops there (`MaxIter`). (The cap no longer depends on the mirror: the position claim is the
  separate, shorter-or-equal `cmp_nsearch`.) `cap_first_bad` is the first search outside the direction bound on the generating
  platform (macOS); the cap is at or below it. `caps.csv` holds the per-search mirror and direction ratios of the *uncapped* run
  behind each capped row.

  | run | cap (margin rule) | first search outside the direction bound (macOS) | comparison prefix `cmp_nsearch` | Linux CI evidence (first outside) |
  |---|---|---|---|---|
  | `m1_rosen5` | 5 | 42 (direction 81.0) | 5 | 7 (run 46132168523, earlier mirror scale) |
  | `m3_rosen5` | 23 | 55 (64.1) | 6 | 25 (run 46133315711) |
  | `m1_quad10_k1e2` | 13 | 15 (113.6) | 13 | 16 (run 46132168523) |
  | `m1_powell4` | 13 | 15 (438.5) | 13 | 15 |
  | `m3_quad10_k1e2` | 24 | 26 (65.8) | 24 | 26 |

  The caps of `m1_rosen5` and `m3_rosen5` come from Linux evidence gathered with the earlier (compounding-scale) criterion; they
  are kept as the committed run lengths (shorter than SciPy's direction bound requires, and not shorter than the prefix), and
  the position claim for them is `cmp_nsearch` (5 and 6 line searches). A cap is valid iff `cap ≤ cap_first_bad`; the margin rule
  (above) keeps it 2 below the smallest observed first-outside index.

  The maintainer proposed that the per-search ratio should be monotone up to the cap. It is not (several decreases before the
  cap in every capped run; only the running maximum is monotone, which is a tautology), and the test does not pretend it is.
  `lbfgs_replay.rs::caps_cannot_hide_a_disagreement` checks, for each capped row, that the replay agrees on every request of the
  comparison prefix; that every search before the cap is inside the direction bound and `cap_first_bad` is at or after the cap and
  really outside it; that every search of the prefix is inside the mirror bound; and that the prefix ends at the cap or at a search
  that exceeds the mirror bound. `only_a_recorded_cap_shortens_a_run` checks that no other run is shortened.
* **Largest observed ratios per group** (replayed runs; the mirror ratio over the *whole* run, so it exceeds `C_X / 4` where the
  prefix is shorter than the run; SciPy direction ratio; runs with a shortened prefix / runs): `default` 3.1e6, 7.5 (3/10);
  `ftol0` 3.1e6, 7.5 (2/4); `memory` 1.8e3, 44.4 (1/7); `tight` 29, 14.7 (1/4); `live` 3.1e6, 7.5 (3/6); `termination` 0.73, 1.6 (0/3);
  `maxiter_order` 3.1e6, 1.9 (3/5); `maxfun` 1.4e3, 1.9 (1/4); `maxls` 3.0e3, 7.5 (2/3); `search` 1.4e3, 9.1 (2/3). Inside the
  prefixes the mirror ratio is ≤ 8 by construction (the Rust implementation reaches 5.5 on the committed data).
* **A finding that bounds what replay can prove: Rosenbrock-5 with `maxcor = 1`.** Run to its end (78 iterations) the
  mirror's ratio reaches 1.8e5 (3e5 for SciPy's own direction error against the exact one in the same run) although both
  implementations are correct: last-digit differences between two correct implementations are amplified by the
  ill-conditioning of the problem, iteration after iteration, so a replay of requested points can only vouch for a prefix of
  the run, and how long that prefix is depends on the problem and the memory, not on the care of the implementer. Past it the
  counts and terminations stop being comparable point by point; the live tests (`lbfgs_live.rs`) cover the converged ends
  by solution, not path.
* Other bounds used by the tests: `C_DIR = 128` (SciPy vs exact, above); `C_TWOLOOP = 16` (Rust's two-loop vs exact
  direction, observed 1.34); `|γ_scipy/γ_exact − 1| ≤ 64 ε` (SciPy forms `dr = (gd − gdold) α`, whose rounding is the
  difference: observed 16 ε); the dense-matrix and secant tests of the two-loop use `4 (2m+1) n ε S`, 2% of which is
  observed.

## SciPy 1.16.3 facts these data pin

* A failing line search costs exactly `maxls` evaluations. `mainlb` tests `iback >= maxls` right after `lnsrlb` returns,
  *before* the driver is asked to evaluate the (`maxls`+1)-th trial, so that trial is never evaluated; the `nfgv--` only
  undoes the internal counter. `maxls1_rosen2_first`: `nfev = 2`.
* `maxfun` is tested only at `NEW_X`, with `>`, after `maxiter`: `maxfun1_rosen2` ends with `nfev = 3` (the search in
  progress is not interrupted).
* `maxiter` is tested before the gradient and function tests of the next entry: `maxiter_eq_k_*` report `MaxIter`
  at the iterate where the free run reports `GradTol` or `FTol`.
* After a failed search with `col > 0` the memory is reset and the retry is steepest descent with `stp = 1` (the first
  trial is `x − g`); the first search of a run has `stp = min(1/‖d‖, 1e10)`.
* `H₀ = γ I` with `γ = sᵀy / yᵀy` of the newest pair (`theta = rr/dr`); with an empty memory `d = −g` exactly.
* After an `ABNORMAL` end (`line_search_failed`) SciPy's `res.fun` is the `f` of the last *trial*, not of the restored
  `res.x`: the driver rebinds `f` to the float the objective returned, so `mainlb`'s restore of `f` never reaches it
  (`res.x` and `res.jac` are restored). The `f` column of `runs.csv` has this value for those runs; the Rust state keeps
  `f` consistent with `x`, and `lbfgs_replay.rs` pins both facts.
* `maxiter = 0` and `maxfun = 0` run one iteration (3 evaluations on Rosenbrock-2); a negative `gtol` is accepted
  silently; `maxcor = 0` is `ERROR: M <= 0`, `ftol < 0` is `ERROR: FACTR < 0`, `maxls = 0` is a `ValueError`.
