# Reference data of `minimize::lbfgs`

SciPy 1.16.3 runs of `scipy.optimize.minimize(method="L-BFGS-B", bounds=None)`, recorded for the tests
`../../lbfgs_replay.rs`, `../../lbfgs_direction.rs`, `../../lbfgs_live.rs` and the unit tests of
`../../../src/lbfgs/twoloop.rs`. Generated by `scripts/gen_minimize_lbfgs_reference.py`
(`uv run scripts/gen_minimize_lbfgs_reference.py` from the repository root; regenerating is a separate commit).
Tracking issue: tensor4all/tenferro-sci-rs#40.

Produced on macOS arm64, Python 3.12, SciPy 1.16.3, NumPy 2.3.5, mpmath 1.3.0 (Accelerate BLAS, Apple libm); the
versions and the date are in the `#` header lines of every file. The CI platform (ubuntu-24.04, OpenBLAS) runs `--check` in the `minimize-reference` job; its first run found the
platform dependence described below.

## The protocol: what exactly was called

Every run is executed twice, and the generator asserts that the two agree on the whole sequence of evaluated points,
the final point, `nit`, `nfev`, `status` and `message`:

1. **The public call**, with *every* option passed explicitly (the `call` column of `runs.csv`; commas are replaced by
   semicolons in the file):
   `minimize(fun, x0, jac=True, method='L-BFGS-B', bounds=None, options={'maxcor': …, 'ftol': …, 'gtol': …,
   'maxfun': …, 'maxiter': …, 'maxls': …})`. SciPy's defaults are `maxcor=10, ftol=2.220446049250313e-09 (=1e7 eps),
   gtol=1e-5, maxfun=15000, maxiter=15000, maxls=20`. `maxls` is recorded for every run.
2. **A replica of `_minimize_lbfgsb`'s loop** (`_lbfgsb_py.py`) around `scipy.optimize._lbfgsb.setulb`, which reads SciPy's
   internal state at every request: `isave` (`col`, `head`, `iter`, `iupdat`, `nskip`, `ifun`), `dsave` (`theta`, `stp`)
   and the workspace `wa` (the stored pairs `S`, `Y`, the direction `d`, the saved point `t` and gradient `r`). The
   workspace layout is the partition `setulb` computes (`__lbfgsb.c`); the indices `mainlb` uses are shifted by 21 in the
   array `setulb` receives. This is how restarts (`col` dropping to 0 at `iter > 0`), the pairs and the direction are
   known, not inferred.

SciPy's `message` is mapped to the Rust `Termination` through the task code (not the `status` integer, which is 1 for an
`ABNORMAL` end when `nfev > maxfun`): `CONVERGENCE: NORM OF PROJECTED GRADIENT <= PGTOL` → `grad_tol`, `…RELATIVE
REDUCTION OF F…` → `f_tol`, `STOP: TOTAL NO. OF ITERATIONS REACHED LIMIT` → `max_iter`, `STOP: TOTAL NO. OF F,G
EVALUATIONS EXCEEDS LIMIT` → `max_eval`, `ABNORMAL` → `line_search_failed`.

Nothing in the data is a NaN or an infinity: SciPy's behaviour there (it resets the memory and burns the remaining
`maxls` trials; NaN at `x0` gives `ABNORMAL` after 21 evaluations) is deliberately *not* ours (decision (b) of #38: stop
at the last finite iterate), so those paths are tested with hand-fed values in `../../lbfgs_termination.rs` and not replayed.

## Files

| File | Contents |
|---|---|
| `caps.csv` | per line search, the mirror and direction ratios of the uncapped run behind each capped row (see "Which runs are capped") |
| `runs.csv` | one row per run: problem, `x0`, options, the exact call, `maxiter_cap`, SciPy's `status`, `message`, `nit`, `nfev`, `njev`, `nskip`, number of restarts, final `x`, `f`, `‖g‖∞`, the Rust `termination`, and the two calibration statistics `dir_ratio` and `mirror_ratio` (below) |
| `evals.csv` | every evaluation SciPy requested, in order: `x`, `f`, `g`, the search it belongs to (−1 for the start), `ifun` (index within the search), `accepted` (the iterate that became `x` after it), `x_scale`, `x_slack` |
| `searches.csv` | one row per line search: `iter`, `col`, `gamma_scipy` (= 1/θ), `gamma_exact`, `stp0`, `x_base`, `g_base`, SciPy's direction `d`, the exact direction `d_exact` (mpmath, 60 digits), `d_scale`, the ids of the stored pairs |
| `pairs.csv` | the `(s, y)` pairs as SciPy stored them in `S`, `Y` (id `p` is per run) |
| `divergences.csv` | runs whose number of `setulb` requests differs from SciPy's `nfev` (`ScalarFunction` caches a repeated `x`): empty |

Vectors are `;`-separated; floats are `repr(float)` (shortest round trip), read back exactly by Rust.

Problems (the Rust tests mirror them in `tests/lbfgs_common/mod.rs`): Rosenbrock n = 2 (two starts) and n = 5, Beale,
Himmelblau, Powell's singular function, and the quadratics `½(x−x*)ᵀA(x−x*)`, `A = P diag(λ) P`, `P = I − 2uuᵀ`,
`u ∝ (1,…,n)`, `λᵢ = κ^(i/(n−1))` (κ = 1, 1e2, 1e4; n = 5, 10), `x* = (1,…,n)`, `x0 = 0`.

| group | runs | what it pins |
|---|---|---|
| `default` | every problem, SciPy's defaults | `GradTol` and `FTol` after k iterations |
| `ftol0` | `ftol = 0` | only the gradient test, `maxiter`, `maxfun` or a failure can stop |
| `memory` | `maxcor` = 1, 3, 50 | the ring buffer wraps (five runs capped by `maxiter_cap`, see below) |
| `tight` | quadratics, small `gtol`, `ftol = 0` | `GradTol` at a stated tolerance |
| `termination` | start at the minimizer; `maxiter = 1`; large `ftol` | `GradTol` with 0 iterations and 1 evaluation; `MaxIter`; `FTol` |
| `maxiter_order` | `maxiter = k` and `k + 1` where the free run ends at k | `MaxIter` wins over `GradTol` and `FTol` at the same iterate |
| `maxfun` | `maxfun` = 1, 5, 10, 20 | `maxfun` is tested after an accepted iteration only, with `>` |
| `maxls` | `maxls` = 1, 2, 3 on Rosenbrock-2 | `maxls` counting; the retry after a failed search |
| `search` | first candidates found by a deterministic search | a restart that ends in `GradTol`, `FTol`, `LineSearchFailed` |

Not recorded: a run with a skipped update (`nskip > 0`); the deterministic search over `maxls` and the problems found
none. The skip rule is covered by the unit tests of `src/lbfgs/memory.rs` instead.

Not recorded either: a line search that ends in a `dcsrch` *warning* (rounding errors, xtol, stpmax, stpmin). All 1021
searches that ended with an accepted step ended with `CONVERGENCE`. `lnsrlb` accepts a warning like a convergence (task
`NEW_X` at the last trial, even when `f` increased), so this is pinned by a hand-fed scenario instead: the generator's
`scripted_checks()` feeds SciPy 1.16.3 a scripted sequence of `(f, g)` (x0 = [0], f0 = 4, g0 = [−1]; then (3.5, −0.95),
then (10, 1) four times) and asserts the requests `0, 1, 5, 1.3552244689139858, 1.0030498702469033, 1.0`, the result
`CONVERGENCE: RELATIVE REDUCTION OF F`, `nit = 1`, `nfev = 6`, `x = [1]`, `f = 10`: the search ends with
`WARNING: XTOL TEST SATISFIED`, the last trial becomes the iterate although `f` rose from 4 to 10, and the one-sided
function test stops the run. `../../lbfgs_termination.rs` replays the same script.

## What `--check` compares

`uv run scripts/gen_minimize_lbfgs_reference.py --check` regenerates everything in memory, compares and writes nothing.
It prints a summary per file and column (mismatch counts, the largest absolute and relative difference, the largest ratio to
the tolerance) and **every mismatch of an exact column in full**, with the list of runs whose path or options changed, so
one CI log answers "did any run change its counts or termination on this platform". Exit 1 on any exact mismatch, any
trajectory value outside its tolerance, or any committed cap that leaves the bounds on the running platform.

Why this is needed: SciPy's trajectory differs at rounding level between platforms (Accelerate/Apple libm vs
OpenBLAS/glibc: the quadratics' matrix–vector products and the dot products inside SciPy's C code sum in a different order,
and the Rosenbrock problems amplify it). The first Ubuntu 24.04 run (PR #41, CI run 46132168523) showed 764 mismatches: the
final `ginf` of the same run differs in the 7th digit, and the platform-dependent choices of the generator changed.

| kind | columns | rule |
|---|---|---|
| exact | ids, options (`ftol`, `gtol`, `x0` as floats), `call`, `message`, `termination`, `nit`, `nfev`, `njev`, `nrequests`, `nskip`, `nrestart`, `nsearch`, `maxiter`, `maxiter_cap`, `replay`, the keys and the number of rows of every file, `accepted`, `search`, `ifun`, `col`, `iter`, `restart` | string equality. A difference means the path of a recorded run changed on that platform: the run leaves the parity set with a documented reason; the check is never loosened |
| trajectory (SciPy's own values) | `evals.csv` `x`, `f`, `g`; `runs.csv` `x`, `f`, `ginf`; `searches.csv` `x_base`, `g_base`; `pairs.csv` `s`, `y` | within a tolerance **derived from the committed scales** (below) |
| diagnostic | `x_scale`, `x_slack`, `d`, `d_exact`, `d_scale`, `gamma_*`, `stp0`, `dir_ratio`, `mirror_ratio`, `cap_first_bad`, `uncapped_nsearch`, `caps.csv` | not compared; the generator checks the regenerated ones against their bounds (a run, or a committed cap, outside the bounds on the running platform aborts with a message) |

Tolerances of the trajectory columns (ε = 2⁻⁵², `C_X = 32`, the committed `x_scale`, `x_slack`; `L` = largest ‖y‖/‖s‖ over the
recorded pairs of the run, n the dimension), as #39 derives `dphi_scale`:

* `|Δxᵢ| ≤ C_X ε x_scaleᵢ + 2 x_slackᵢ`: the replay bound of two correct implementations; both SciPy runs deviate from the
  exact direction by at most `x_slack`.
* `|Δgᵢ| ≤ 4 L ‖tol_x‖₂ + 8 n ε (|gᵢ| + L ‖x‖₂)`: `g` is `L`-Lipschitz along the path (mean value theorem; `L` from the
  secant ratios, the factor 4 is a margin for segments the other path took), plus the rounding of evaluating `g`.
* `|Δf| ≤ ‖g‖₂ ‖tol_x‖₂ + 2 L ‖tol_x‖₂² + 8 n ε (|f| + ‖g‖₂ ‖x‖₂)`: first-order Taylor.
* `pairs`: `s` differs by at most `2 max_k tol_x`, `y` by at most `2 max_k tol_g` (a difference of two iterates/gradients);
  `runs.csv` `x`, `f`, `ginf` use the tolerance of the last accepted (last) evaluation of the run.

**Caveat found while deriving them:** `x_scale` is the absolute-value recursion of the two-loop (Σ|terms| with every sign
positive), which compounds along the recursion: on `default_rosen2` it grows from 1 to 4.6e15 over 36 iterations. A tolerance
of `C_X ε x_scale` is therefore vacuous late in such runs (about 1 in x at the end of `default_rosen2`), for the replay as well
as for this check, while it is tight early. The bounds are valid but pessimistic; a tighter forward-error measure (per
operation `Σ|terms|` with the actual values, not the abs-recursion) would make both claims sharper. Reported to the
maintainer, not changed here (it would change every recorded ratio).

**Caps are platform-independent.** The cap of a run is the minimum over the checked platforms of the largest prefix of line
searches inside the bounds: macOS arm64 (committed first) 25, 15, 15, 26, 26 and Ubuntu 24.04 x86_64 (CI run 46132168523,
values from its log) 7, 16, 15, 29, 26 for `m1_rosen5`, `m1_quad10_k1e2`, `m1_powell4`, `m3_rosen5`, `m3_quad10_k1e2`; hence 7,
15, 15, 26, 26. The generator takes the caps, the `tight` gtols, the search picks and the counts-only live rows from fixed
tables, so no platform-dependent choice remains; `--check` verifies that every committed cap is still inside the bounds on the
running platform and fails only if it is not (never by choosing a different cap). The generating platform's first search
outside the bounds is the `cap_first_bad` column (diagnostic).

The generator also asserts the coverage the tests rely on (every termination, a restart ending in each of three ways, the
counting cases).

## How the tolerance was derived

The replay feeds SciPy's `(f, g)` to the Rust state and compares the requested point with SciPy's. A requested point is
`x_base + α d`, `d = −H g` (two-loop), α from the line search. Rust's `x_base` is its own accepted iterate, so the error
accumulates over the steps taken. For component `i` the test allows

    |x_rust,i − x_scipy,i|  ≤  C_X · ε · x_scale,i  +  x_slack,i          (ε = 2⁻⁵², C_X = 32)

* `x_scale,i = cum_i + |x_base,i| + |α| d_scale,i`: the absolute-value scale of the computation (Higham,
  *Accuracy and Stability of Numerical Algorithms*, 2nd ed., §3.1: a sum or dot product of terms is computed to within
  `γₙ Σ|terms|`, `γₙ = nε/(1−nε)`). `d_scale,i` is `Σ|terms|` of the two-loop recursion for component `i`, evaluated with
  all signs positive in 60-digit arithmetic (`searches.csv`); `cum_i` is the sum over the accepted steps so far of
  `|α_j| d_scale,j,i + |x_{j+1,i}|`.
* `x_slack,i`: the sum over the steps so far (and the current one) of `|α_j| · |d_scipy − d_exact|_i`: SciPy's *own*
  deviation from the exact direction, measured against mpmath, not assumed. SciPy's compact-representation direction is
  less accurate than a two-loop recursion on small memories: relative to `d_scale` it deviates by up to **43.8 ε** on the
  committed runs (`dir_ratio`), against 1.3 ε for a float64 two-loop recursion (`../../../src/lbfgs/twoloop.rs`,
  checked on all 1028 searches).
* **`C_X = 32` is measured, not derived from `n` and `m`.** A float64 mirror of the algorithm the Rust code follows
  (`Mirror` in the generator: the ask/tell state machine described in the module docs of `minimize::lbfgs`, on Python's
  `DCSRCH._iterate`, which `linesearch::MoreThuente` ports) replays every run. The generator keeps a run (or the prefix
  of one) only while the mirror agrees on every count and termination and the ratio
  `(|Δx| − x_slack) / (ε x_scale)` of each line search (`mirror_ratio`) is at most `C_X / 4 = 8`, and SciPy's own direction
  is within `C_DIR / 2 = 64` of exact (`dir_ratio`, `C_DIR = 128`). The factor 4 is a margin: a throwaway implementation
  of the algorithm was up to twice as far from SciPy as the mirror (27.5 against the mirror's 13.6 on a longer prefix), so
  the constant `C_X` is never raised and the prefix is shortened instead. The Rust implementation is independent of the
  mirror; its PR must report its own maximum. If it exceeds the bound, that is a finding to explain, not a constant to widen.
  The constant is one named value (`C_X` in `tests/lbfgs_common/mod.rs`) and every replay failure prints the observed
  maximum ratio and the bound.
* **Which runs are capped, and why the cap is data.** Five runs of the `memory` group (`maxcor` = 1, 3) leave the bounds
  after some line searches. Their `maxiter` is the `maxiter_cap` column of `runs.csv` (empty = `none` for every other run),
  chosen as **the largest prefix inside the bounds on every checked platform** (see "What `--check` compares"): every line
  search before the cap has mirror ratio ≤ `C_X / 4` and SciPy direction error ≤ `C_DIR / 2`, and the run stops there (`MaxIter`).
  `cap_first_bad` is the first search outside the bounds on the generating platform (macOS); the cap is at or below it. `caps.csv`
  holds the per-search ratios of the *uncapped* run behind each capped row, so the claim is checkable.

  | run | cap (searches) | macOS first search outside | Ubuntu (CI) first search outside | of uncapped | macOS: search outside, mirror / direction | exceeds |
  |---|---|---|---|---|---|---|
  | `m1_rosen5` | 7 | 25 | 7 | 78 | 11.7, 0.9 | mirror ratio above `C_X / 4` |
  | `m3_rosen5` | 26 | 26 | 29 | 58 | 10.5, 0.0 | mirror ratio above `C_X / 4` |
  | `m1_quad10_k1e2` | 15 | 15 | 16 | 73 | 0.9, 113.6 | SciPy's own direction error above `C_DIR / 2` |
  | `m1_powell4` | 15 | 15 | 15 | 58 | 1.4, 438.5 | SciPy's own direction error above `C_DIR / 2` |
  | `m3_quad10_k1e2` | 26 | 26 | 26 | 56 | 0.7, 65.8 | SciPy's own direction error above `C_DIR / 2` |

  The maintainer proposed that the per-search ratio should be monotone up to the cap. It is not (11–15 decreases before the
  cap in the Rosenbrock rows, 5–13 in the others; only the running maximum is monotone, which is a tautology), and the
  test does not pretend it is. `lbfgs_replay.rs::caps_cannot_hide_a_disagreement` checks the condition that does hold and
  that excludes "we stopped before it got worse": the replay agrees on every request up to the cap, every search before
  the cap is inside the bounds, and the generating platform's first search outside the bounds (`cap_first_bad`) is at or after the
  cap and really is outside one (a cap below it, as for `m1_rosen5`, is justified by the other platform). `only_a_recorded_cap_shortens_a_run`
  checks that no other run is shortened (the only other runs with a small `maxiter` are the tests of the iteration limit
  itself).
* **Largest observed ratios on the uncapped runs** (mirror ratio, SciPy direction ratio; all runs of a group that have no
  cap): `default` 0.73, 7.5; `ftol0` 0.73, 7.5; `memory` (`m3_powell4`, `m50_quad10_k1e2`) 0.64, 1.7; `tight` 0.21, 14.7;
  `termination` 0.73, 1.6; `maxiter_order` 0.30, 1.9; `maxfun` 0.73, 1.9; `maxls` 0.73, 7.5; `search` 0.73, 9.1. For the
  capped runs, inside their cap: 7.7 and 44.4.
* **A finding that bounds what replay can prove: Rosenbrock-5 with `maxcor = 1`.** Run to its end (78 iterations) the
  mirror's ratio reaches 1.8e5 (3e5 for SciPy's own direction error against the exact one in the same run) although both
  implementations are correct: last-digit differences between two correct implementations are amplified by the
  ill-conditioning of the problem, iteration after iteration, so a replay of requested points can only vouch for a prefix of
  the run, and how long that prefix is depends on the problem and the memory, not on the care of the implementer. Past it the
  counts and terminations stop being comparable point by point; the live tests (`lbfgs_live.rs`) cover the converged ends
  by solution, not path.
* Other bounds used by the tests: `C_DIR = 128` (SciPy vs exact, above); `C_TWOLOOP = 16` (Rust's two-loop vs exact
  direction, observed 1.34); `|γ_scipy/γ_exact − 1| ≤ 64 ε` (SciPy forms `dr = (gd − gdold) α`, whose rounding is the
  difference: observed 16 ε); the dense-matrix and secant tests of the two-loop use `4 (2m+1) n ε S`, 2% of which is
  observed.

## SciPy 1.16.3 facts these data pin

* A failing line search costs exactly `maxls` evaluations. `mainlb` tests `iback >= maxls` right after `lnsrlb` returns,
  *before* the driver is asked to evaluate the (`maxls`+1)-th trial, so that trial is never evaluated; the `nfgv--` only
  undoes the internal counter. `maxls1_rosen2_first`: `nfev = 2`.
* `maxfun` is tested only at `NEW_X`, with `>`, after `maxiter`: `maxfun1_rosen2` ends with `nfev = 3` (the search in
  progress is not interrupted).
* `maxiter` is tested before the gradient and function tests of the next entry: `maxiter_eq_k_*` report `MaxIter`
  at the iterate where the free run reports `GradTol` or `FTol`.
* After a failed search with `col > 0` the memory is reset and the retry is steepest descent with `stp = 1` (the first
  trial is `x − g`); the first search of a run has `stp = min(1/‖d‖, 1e10)`.
* `H₀ = γ I` with `γ = sᵀy / yᵀy` of the newest pair (`theta = rr/dr`); with an empty memory `d = −g` exactly.
* After an `ABNORMAL` end (`line_search_failed`) SciPy's `res.fun` is the `f` of the last *trial*, not of the restored
  `res.x`: the driver rebinds `f` to the float the objective returned, so `mainlb`'s restore of `f` never reaches it
  (`res.x` and `res.jac` are restored). The `f` column of `runs.csv` has this value for those runs; the Rust state keeps
  `f` consistent with `x`, and `lbfgs_replay.rs` pins both facts.
* `maxiter = 0` and `maxfun = 0` run one iteration (3 evaluations on Rosenbrock-2); a negative `gtol` is accepted
  silently; `maxcor = 0` is `ERROR: M <= 0`, `ftol < 0` is `ERROR: FACTR < 0`, `maxls = 0` is a `ValueError`.
